## はじめに

- [RunPod](https://www.runpod.io/) でGPUを借り、 [∂hosts ─ 幽霊文字生成環境【技術編】](https://semi.uyupun.tech/presentations/2026/11-04/kazukichi/) で扱ったGAN(Generative Adversarial Network)の学習を回してみた
- 今回は、サービスを選ぶまでの経緯と、使ってみて分かった速度や在庫の事情を紹介する

## 学習の要件

- これまで学習はローカルのMac(Apple Silicon)で、PyTorchのMPS(Metal Performance Shaders)バックエンドを使って回していた
- フルスケール学習の1回に半日かかるうえ、同時に回せるのも2本までで、スケーラビリティにも問題があった
- モデル自体はLLMと比べて小さく、VRAMの容量ではなく演算速度が効く規模
- 「一晩放置すれば良い」は許容せず、セットアップの手間込みの実時間でローカルより確実に速くなることを必須条件にした
- 今後何度も繰り返すため、初回のセットアップにかかる手間は一度払えばよい投資として許容できる
- 途中で中断されると必須条件そのものが壊れるため、安さよりも中断しないことを優先する

## RunPodとは

- GPUやCPUを分単位の課金で借りられるクラウドサービス
- 借りる単位はPodで、PyTorchなどが入ったDockerイメージのテンプレートから選ぶか、任意のコンテナレジストリから持ち込む
- データセンターで運用されるSecure Cloudと、個人の提供者のマシンをピアツーピアで繋ぐCommunity Cloudの2通りがあり、後者のほうが安い
- Podとは別にNetwork Volumeを借りられ、Podを終了しても消えない領域に学習コードやデータセットを置いておける
- Network VolumeはSecure CloudのPodにしか付けられないため、今回は基本的にSecure Cloudを使っている
- またNetwork Volumeはデータセンターに紐づくため、付けるPodも同じデータセンターで作ることになる
- 月額固定のプランはなく、クレジットをチャージして使った分だけ消費する形
- RTX 4090は、高い側のSecure Cloudでも1時間あたり$1を下回る

## 類似サービスとの比較

- 候補として、RunPod / Vast.ai / Lambda Labs / AWS等のハイパースケーラ / Colab ProやKaggleを比較した
- Lambda Labsは価格帯が大きめのカードに寄っており、小型GPUの安価な枠が見当たらないため、今回の規模ではコスト効率が悪い
- ハイパースケーラはアカウントやIAM周りのセットアップの手間が増える割に、単発の小規模なGPUジョブでは明確な利点がない
- Colab ProやKaggleは安価だが、セッション時間の制限や制御の自由度の低さがあり、数時間の無人実行には専用のPodのほうが向く
- 分単位の課金でPodを起動できるRunPodとVast.aiが要件に合い、最終的にはRunPodを選んだ
- 決め手の1つは安定性で、RunPodはデータセンター運用のSecure Cloudと個人提供のCommunity Cloudがプランとして分かれているため、前者を選ぶだけで済む
- Vast.aiにも認証済みのデータセンターのホストや信頼性のスコアはあるが、同じマーケットプレイス内の属性のため、出品ごとに見極める必要がある
- 公式が保守する `runpod/pytorch` テンプレートはCUDA / cuDNN / PyTorchのバージョンが噛み合っており、セットアップでつまずく確率を下げられる
- Vast.aiにはない標準機能としてNetwork Volumeがあり、2回目以降は環境とデータを載せたまま新しいPodに付け替えるだけで済むと見ていた
- 先述の中断しない方針から、Spot Pod(他のユーザがより高い価格を出すと停止される代わりに、料金が半分ほどになる枠)は使わず、on-demandで借りている

## runpodctlでの操作

- APIキーとSSH鍵を設定すれば、CLIの `runpodctl` 経由でPodの作成から削除まで操作できる
- Web UIを触らずに一連の作業が完結するため、 `runpodctl` とSSHのコマンドをいくつかのシェルスクリプトにまとめ、Claude Codeにそれを実行してもらっていた
- 用意したのは、Podの作成 / コードと学習データの転送 / 学習の起動 / 進捗の確認 / 結果のダウンロード / Podの削除にあたる6種類
- GPUの機種を複数渡して空きがあるものを順に試す、学習はSSHを切っても止まらないようにする、といった運用上の対処もスクリプト側に寄せた
- Podの作成は課金が発生するため1つずつ行い、失敗したときは `runpodctl pod list` で作られていないことを確かめてから条件を変える

## 学習速度の変化

- 借りるGPUは、VRAMの容量が問題にならない規模であることと、1時間あたり$1を下回る価格から、RTX 4090を基本にしていた
- ローカルで律速になっていた行列演算が十分に速くなり、段違いの速度で学習が回るようになった
- GANの学習ではGPUをほぼ使い切っており、借りた機種の性能がそのまま速度に効く

## 学習の並列化

- GPUに余裕があるときは、同じPodで複数の学習を回せた
- 並列化するとGPUがほぼ100%まで埋まり、スループットの低下もあまり見られないため、効率良くリソースを使える
- 1つの学習でGPUを使い切ってしまう場合は、Podを複数立てて並列に回す手もある
- 課金は借りている時間に対して発生するため、同じPodに載せる限りは何本回しても費用が変わらないのはありがたい

## 在庫とリージョン

- 時間帯によって空いているリージョンが大きく異なり、タイムゾーンが関係していそう
- 在庫は常に薄いわけではないが、薄いタイミングでは狙ったGPUが数秒差で取られてしまう(誰かが大量に確保しているのかもしれない)
- そのためAIで定期実行を流し、空きが出たら即確保する運用にしている
- ハイエンドGPUはかなり余っている一方で、ミドルレンジ帯は選べる数がそもそも少ない
- 提供側の利益が薄いのかもしれないが、こちらをもっと厚くしてほしい

## ホストのばらつき

- GPUをRTX 4090で揃えても、CPU側には当たり外れが残る
- 在庫が薄いときは選ぶ余地がなくなるため、相対的に外れのホストを引きやすい
- 外れを引くとCPUが律速になり、GPUの性能を使い切れずに速度が出ない
- 学習に時間がかかりすぎるようになってH100やRTX PRO 6000に上げたこともあるが、予想に反して遅くなった
- 機種を上げても縮まらないため、やはりホストのCPU側に引っ張られていたのだと見ている

## Network Volumeの置き場所

- 在庫が薄いときにまともなホストのPodを探すと、確保できるリージョンが散らばる
- 先述のデータセンターの制約があるため、散らばった分だけNetwork Volumeを作っておく必要が出てくる
- そのため選定時に見込んでいたほど、Network Volumeを前提にした使い回しはできなかった
- データの永続化を諦めてPod内で完結させる手もあるが、そのぶん毎回のセットアップが長くなる
- データセンターに依存しないGlobal Volumeもあるが、現時点ではベータの機能
- 学習やチェックポイントのような書き込みの多い用途にはNetwork Volumeのほうが向くと公式も案内しているため、そのまま置き換えられるものではない

## おわりに

- クラウドのGPUは高価だという印象を勝手に持っていたが、実際には現実的な価格で借りられた
- 将来的にはローカルに高性能なGPUを置くことも考えていたが、この価格帯で済むなら不要かもしれないと見ている
