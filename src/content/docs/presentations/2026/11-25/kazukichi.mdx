## はじめに

- 展示用の映像作品を無人で表示し続けるキオスク端末を、Raspberry Pi(以下ラズパイ)で構築した
- 用途は映像だが、この構成自体は表示するものの種類に依らない
- 今回は、ハードウェアとOSの選定から、実機でつまずいた箇所までの構築の流れを紹介する

## キオスク端末とは

- 用途を1つに限定し、単一のアプリケーションだけを全画面で表示し続ける端末
- 駅の券売機や店舗の注文端末、美術館の案内ディスプレイなどが該当する
- OSのデスクトップやブラウザのUIを見せず、利用者がそこから他の操作へ抜け出せないようにするのが基本
- 今回作るのは鑑賞者が一切操作しない表示専用の端末だが、操作を受け付ける場合でも構成はほとんど変わらない

## 構築の要件

- 展示中は無人で動き続けるため、アプリが落ちても自動で復帰すること
- 会場へ持ち運ぶため、ディスプレイごと手で運べるサイズに収めること
- 展示する作品は複数あるため、どの端末にどの作品を表示するかを手元のPCから切り替えられること
- 作品にはWebアプリのものと実行ファイルのものがあるため、どちらも同じ仕組みで表示できること
- 端末を作り直しても同じ状態に戻せるよう、構築手順をコードとして残すこと

## ハードウェア構成

- 本体はラズパイ5で、CPUとGPUの性能は8GBモデルと変わらないため、差額を踏まえてメモリ4GBのモデルにした
- ディスプレイは公式の [Touch Display 2](https://www.raspberrypi.com/products/touch-display-2/) (7インチ)で、使わないタッチ機能の分だけ価格は高くつくが、ラズパイ本体を背面に固定できるため持ち運ぶ構成には向いている
- DSI(Display Serial Interface)接続のためHDMIケーブルが要らず配線を減らせるが、リボンケーブルは脆いうえに挿しにくく、着脱には気を遣う
- 長時間の連続稼働でサーマルスロットリングが起きないよう、公式の [Active Cooler](https://www.raspberrypi.com/products/active-cooler/) を載せている
- ラズパイ5は消費電力が上がっており、非対応の電源では動作が不安定になることがあるため、電源も [Raspberry Pi 27W USB-C Power Supply](https://www.raspberrypi.com/products/27w-power-supply/) にした
- ストレージはシリコンパワーの64GB microSDカードにしたが、展示期間を通した書き込みに耐えられるかは不安が残る

## OSとキオスク環境の選定

- OSはRaspberry Pi OS Lite(64-bit)を選び、その上に軽量なWaylandコンポジタである [labwc](https://labwc.github.io/) を載せた
  - Waylandコンポジタは各アプリの描画結果を画面に合成し、入力を振り分けるプロセスで、X11ではXサーバとウィンドウマネージャに分かれていた役割を1つで担う
- 公式ディスプレイのDSIパネルやラズパイ5固有のGPUドライバは、Raspberry Pi財団がカーネルやファームウェアと一体で保守しているため、Ubuntuや自前の最小イメージより追従が早い
- Desktop版はタスクバーや壁紙といったデスクトップ一式が常駐し、無人で1つのアプリを映すだけの用途では4GBのメモリと起動時間を無駄に使う
- GPUのハードウェアアクセラレーションはDesktop版と同じドライバスタックを使うため、Lite版にしても描画が遅くなることはない
- 展示中ずっと映し続けるには画面の消灯を止める必要もあるが、省電力デーモンを入れていないため、無効化の設定なしで消灯せずに済んでいる
- コンポジタを置かず、DRM(Direct Rendering Manager)/KMS(Kernel Mode Setting)へ直接描画する構成も採れるが、Chromiumにはその経路がなくWaylandかX11が必要なため、Webの作品も扱う以上はコンポジタを置くことになる
- そのコンポジタとしてはキオスクに特化した [cage](https://github.com/cage-kiosk/cage) も候補だったが、labwcはRaspberry Pi OSの既定であり実機での情報量が多いため、こちらを採用した

## SDカードへの書き込み

- Raspberry Pi Imagerは2.0から、イメージの書き込みと [cloud-init](https://cloud-init.io/) の設定ファイルの配置をCLIで一度に行えるため、当初はこれを使うつもりだった
- しかし `rpi-imager --cli` はアンマウント処理がハングする不具合を踏んだため、 `dd` でイメージを書き込む方式に切り替えた
  - ちなみに `/dev/diskN` ではなく生デバイスの `/dev/rdiskN` を指定するほうが速い
- `dd` には設定ファイルを配置する機構がないため、自動マウントされるboot区画へ手で置いている
- デバイスパスを間違えるとそのディスクの中身が失われるため、 `diskutil list` で毎回確認している

```bash
$ sudo dd if=/tmp/raspios-lite-arm64.img of=/dev/rdiskN bs=4m status=progress
```

## cloud-initでの初回設定

- 2025年11月以降のRaspberry Pi OSは、初回起動時の設定が独自の `firstrun.sh` 方式からcloud-init方式に変わっている
- boot区画に `user-data` / `network-config` / `meta-data` の3ファイルを置くと、その内容に沿ってホスト名やユーザが設定される
- 既定のユーザは用意されていないため、ここで鍵認証のユーザを作り、パスワード認証は無効にしておく
- 作ったユーザにはパスワードを設定しないため、Ansibleのbecomeがそのまま通るようsudoをパスワードなしで許可している
- cloud-initだけでは埋まらない設定は `runcmd` で補っている
  - Wi-Fiの地域コードが未設定だと `wlan0` が `rfkill` でソフトブロックされるため、sshdの有効化とあわせてここで設定している
  - 画面とキーボードを直接繋いで作業する場合に備え、キーボード配列とコンソールフォントもここで直している

## Ansibleでのプロビジョニング

- エージェントを常駐させずSSH越しに設定を流せて、何度実行しても同じ状態になるため、プロビジョニングにはAnsibleを選んだ
- 鍵でログインできるようになったら、パッケージの導入 / 自動ログインとlabwc起動の設定 / 作品の取得と展開 / サービスの配置と有効化を一度に流し込む
- ターゲットにPythonがあることを前提にする仕組みだが、Raspberry Pi OSには標準で入っているため下準備は要らない
- ラズパイ向けの専用モジュールには頼らず、 `apt` / `template` / `systemd_service` といった標準モジュールだけで完結させた
- 端末ごとに異なる値(画面の出力名や輝度のパス)はインベントリのグループ変数に置き、ディスプレイの種類ごとにグループを分けている
- 表示する作品はplaybookの外のファイルに切り出し、実行時に渡して切り替える

```bash
$ ansible-playbook -i ansible/inventory.ini ansible/site.yml -e @ansible/works/<作品名>.yml
```

## キオスクの起動構成

- `tty1` への自動ログイン / `.bash_profile` からのlabwc起動 / systemdサービスとしてのアプリ起動、という3層構成にした
- Waylandコンポジタは実際にログインした仮想端末上でしか起動できないため、SSH経由ではなくログイン時に起動させる必要がある
- アプリ本体をlabwcのautostartではなくsystemdサービスにしているのは、 `Restart=always` でクラッシュ時の復帰をsystemdに任せられるため
- Touch Display 2は縦長が標準の向きなので、画面の回転と輝度を作品ごとの変数で指定し、アプリを立ち上げる前に適用している
- Webの作品ならChromiumをキオスクモードで起動し、実行ファイルの作品ならリリースのアーカイブを展開して直接起動する
- Chromiumには、復元ダイアログや初回起動ウィザードを抑止し、無人稼働中に余計な通信もさせないためのフラグを付けている

## 実機でのつまずき

- Lite版の既定のターゲットは `multi-user.target` で `graphical.target` には到達しないため、後者を指定していたサービスが再起動後に自動起動しなかった
  - 手動の `systemctl start` では起動できてしまうため、一度再起動するまでこの問題に気付けなかった
- `chromium-browser` パッケージを入れても `/usr/bin/chromium-browser` は生成されず、実際のコマンドは `/usr/bin/chromium` だった
- SDL2は既定でX11を優先するため、実行ファイルの作品では `SDL_VIDEODRIVER=wayland` を明示してlabwcに繋いでいる
- 毎秒のフレーム数を標準出力に書く作品があり、SDカードへの書き込みを増やさないよう標準出力は捨てている
- 電源をいきなり抜いて実際にファイルシステムを壊したため、必ず `shutdown` を実行し、緑のLEDの点滅が止まってから抜くようにしている

## おわりに

- 会場のWi-Fiは現地に着くまで分からないことが多いため、PCとラズパイをEthernetで直結して接続先をその場で登録する経路を用意しておきたい
- 展示期間に相当する連続稼働はまだ試せていないため、Chromiumのメモリが増え続けるようなら夜間の自動再起動を足すことになる
- 1台分の構成が固まったので、別の作品や別のディスプレイの端末も同じAnsibleで増やせるようにしていきたい
