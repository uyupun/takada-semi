## はじめに

- 展示用の映像作品を無人でも表示し続けられるキオスク端末を、Raspberry Pi(以下ラズパイ)とミニPC(Intel NUC)で構築した
- 用途は映像だが、画面に表示するものであれば、この構成自体は種類に依らない
- [反転する地平、明滅する土着](https://semi.uyupun.tech/presentations/2026/10-05/kazukichi/) や [∂hosts ─ 幽霊文字生成環境【思想編】](https://semi.uyupun.tech/presentations/2026/10-22/kazukichi/) で紹介した作品をはじめ、今後増えていく作品を展示するためのプラットフォームとして作っている
- 今回は、ハードウェアとOSの選定から、2種類の機材を同じ仕組みで扱う構成、会場での運用までを紹介する

## キオスク端末とは

- 用途を1つに限定し、単一のアプリケーションだけを全画面で表示し続ける端末
- 駅の券売機や店舗の注文端末、美術館の案内ディスプレイなどが該当する
- OSのデスクトップやブラウザのUIを見せず、利用者がそこから他の操作へ抜け出せないようにするのが基本
- 今回作るのは鑑賞者が一切操作しない表示専用の端末だが、操作を受け付ける場合でも構成はほとんど変わらない

## 構築の要件

- 展示中は無人で動き続けることもあるため、アプリが落ちても自動で復帰すること
- 会場へ持ち運ぶため、手で運べるサイズに収めること
- 展示する作品は複数あるため、どの端末にどの作品を表示するかを手元の作業用PCから切り替えられること
- 作品にはWebアプリのものと実行ファイルのものがあるため、どちらも同じ仕組みで表示できること
- ラズパイでは性能が足りない作品にはミニPCを使うため、機材が違っても同じ仕組みで構築できること
- 端末を作り直しても同じ状態に戻せるよう、構築手順をコードとして残すこと

## ハードウェア構成

- 会場に有線のネットワークがない前提のため、どちらの機材もネットワークは内蔵のWi-Fiで繋ぐ

### ラズパイ

- 本体はラズパイ5で、差額を踏まえてメモリ4GBのモデルにした
  - CPUとGPUの性能は8GBモデルと変わらない
  - 表示する作品は、4GBでもメモリが足りなくなるとは想定されなかった
- ディスプレイは公式の [Touch Display 2](https://www.raspberrypi.com/products/touch-display-2/) (7インチ)で、使わないタッチ機能の分だけ価格は高くつくが、ラズパイ本体を背面に固定できるため持ち運ぶ構成には向いている
- DSI(Display Serial Interface)接続のためHDMIケーブルが要らず配線を減らせるが、リボンケーブルは脆いうえに挿しにくく、着脱には気を遣う
- ただ、実際に展示で使ってみると反省点も多かった
  - 小型なので、展示の場では作品が目立ちにくい
  - リボンケーブルが抜けやすい
  - 小型の割に高価
- 長時間の連続稼働でサーマルスロットリングが起きないよう、公式の [Active Cooler](https://www.raspberrypi.com/products/active-cooler/) を載せている
- ラズパイ5は消費電力が上がっており、非対応の電源では動作が不安定になることがあるため、電源も [Raspberry Pi 27W USB-C Power Supply](https://www.raspberrypi.com/products/27w-power-supply/) にした
- ストレージはシリコンパワーの64GB microSDカードにした
- 電源をいきなり抜いて実際にファイルシステムを壊したため、必ず `shutdown` を実行し、緑のLEDの点滅が止まってから抜くようにしている

### ミニPC

- 本体はIntel NUC(NUC8i3BEH)で、ストレージはM.2のNVMe SSD
- ディスプレイはHDMIで外部モニタに繋ぐ

## OSとキオスク環境の選定

### OS

- ラズパイのOSはRaspberry Pi OS Lite(64-bit)にした
  - 公式ディスプレイのDSIパネルやラズパイ5固有のGPUドライバは、Raspberry Pi財団がカーネルやファームウェアと一体で保守しているため、Ubuntuや自前の最小イメージより追従が早い
  - Desktop版はタスクバーや壁紙といったデスクトップ一式が常駐し、無人で1つのアプリを映すだけの用途では4GBのメモリと起動時間を無駄に使う
  - GPUのハードウェアアクセラレーションはDesktop版と同じドライバスタックを使うため、Lite版にしても描画が遅くなることはない
- ミニPCのOSは、デスクトップ環境なしの最小構成のDebian 13(trixie)にした
  - Raspberry Pi OS Liteも現在はDebian 13ベースのため、OSを揃えることでパッケージ名や設定の違いをほぼなくせる

### キオスク環境

- アプリを画面に表示する方法には、Waylandコンポジタを置く構成と、DRM(Direct Rendering Manager)/KMS(Kernel Mode Setting)へ直接描画する構成がある
  - Waylandコンポジタは各アプリの描画結果を画面に合成し、入力を振り分けるプロセスで、X11ではXサーバとウィンドウマネージャに分かれていた役割を1つで担う
- ChromiumにはDRM/KMSへ直接描画する経路がなくWaylandかX11が必要なため、Webの作品も扱う以上はコンポジタを置くことになる
- コンポジタとしてはキオスクに特化した [cage](https://github.com/cage-kiosk/cage) も候補だったが、Raspberry Pi OSの既定のコンポジタで、ラズパイでの実例が多い [labwc](https://labwc.github.io/) を採用した
  - labwcは軽量なWaylandコンポジタで、ラズパイとミニPCのどちらにも載せている
- 展示中ずっと映し続けるには画面の消灯を止める必要もあるが、ラズパイでは省電力デーモンを入れていないため、無効化の設定なしで消灯せずに済んでいる

## 構築の流れ

- 構築を、機材ごとに異なるOSのインストールと、機材に依らないAnsibleでのプロビジョニングの2層に分けた
- OSのインストールは、 `kiosk` ユーザでSSHの鍵認証ができる状態にするところまでを担う
- そこから先はAnsibleで共通化し、機材やディスプレイごとの差分はインベントリのグループ変数で吸収する

## OSのインストール

### ラズパイ

- Raspberry Pi Imagerは2.0から、イメージの書き込みと [cloud-init](https://cloud-init.io/) の設定ファイルの配置をCLIで一度に行えるため、当初はこれを使うつもりだった
- しかし `rpi-imager --cli` はアンマウント処理がハングする不具合を踏んだため、 `dd` でイメージを書き込む方式に切り替えた
  - ちなみに `/dev/diskN` ではなく生デバイスの `/dev/rdiskN` を指定するほうが速い
- デバイスパスを間違えるとそのディスクの中身が失われるため、 `diskutil list` で毎回確認している

```bash
$ sudo dd if=/tmp/raspios-lite-arm64.img of=/dev/rdiskN bs=4m status=progress
```

- 2025年11月以降のRaspberry Pi OSは、初回起動時の設定が独自の `firstrun.sh` 方式からcloud-init方式に変わっている
- boot区画に `user-data` / `network-config` / `meta-data` の3ファイルを置くと、その内容に沿ってホスト名やユーザが設定される
  - `dd` には設定ファイルを配置する機構がないため、書き込み後に自動マウントされるboot区画へ手で置いている
- 既定のユーザは用意されていないため、cloud-initで鍵認証のユーザを作り、パスワード認証は無効にしておく
- 作ったユーザにはパスワードを設定しないため、Ansibleのbecomeがそのまま通るようsudoをパスワードなしで許可している
- cloud-initだけでは埋まらない設定は `runcmd` で補っている
  - Wi-Fiの国コードが未設定だと `wlan0` が `rfkill` でソフトブロックされるため、sshdの有効化とあわせてここで設定している
  - 画面とキーボードを直接繋いで作業する場合に備え、キーボード配列とコンソールフォントもここで直している

### ミニPC

- Debian 13のnetinstのISOに、インストーラの質問への回答を書いたpreseedファイルを埋め込んだ
- これにより、USBメモリから起動するだけで最後までインストールが進む
- ISOの書き換えには `xorriso` を使い、UEFI用のGRUBの設定に自動インストールの項目を差し込んで、5秒後に自動で始まるようにしている
  - 元のISOの起動情報は `-boot_image any replay` でそのまま引き継げるため、USBから起動できる形を自前で組み立てる必要はない
- インストール中からWi-Fiで繋ぎ、その設定をインストール後にも引き継がせている
- インストーラはユーザのパスワードを必須とするため、ランダムな文字列のハッシュを入れておく
  - インストール後にパスワードをロックし、ラズパイと同じく鍵認証だけにしている
- `*.local` で到達できるよう、Debianの既定では入らない `avahi-daemon` をpreseedで追加している
- USBメモリへの書き込みはラズパイと同じく `dd` で行い、端末に挿して起動メニュー(NUCは起動時にF10)から選べば、あとは操作なしで完了する

```bash
$ bootstrap/pc/build-iso.sh /tmp/debian-netinst.iso /tmp/kiosk-pc.iso
$ sudo dd if=/tmp/kiosk-pc.iso of=/dev/rdiskN bs=4m status=progress
```

## Ansibleでのプロビジョニング

- エージェントを常駐させずSSH越しに設定を流せて、何度実行しても同じ状態になるため、プロビジョニングにはAnsibleを選んだ
- 鍵でログインできるようになったら、パッケージの導入 / 自動ログインとlabwc起動の設定 / 作品の取得と展開 / サービスの配置と有効化を一度に流し込む
- AnsibleはターゲットにPythonがあることを前提とするが、Raspberry Pi OSには標準で入っており、ミニPCにはpreseedで入れているため下準備は要らない
- 機材向けの専用モジュールには頼らず、一部の例外を除いて `apt` / `template` / `systemd_service` といった標準モジュールだけで完結させた
- 機材やディスプレイごとに異なる値はインベントリのグループ変数に置き、「ラズパイ+Touch Display 2」「ミニPC+HDMIの外部モニタ」のようにグループを分けている
  - 画面の出力名、輝度のパス、追加のパッケージなどがこれにあたる
- 表示する作品の設定はplaybookの外のファイルに切り出し、端末のホスト名と同じ名前のファイルが自動で使われるようにした

## 作品の表示

### 起動の仕組み

- `tty1` への自動ログイン / `.bash_profile` からのlabwc起動 / systemdサービスとしてのアプリ起動、という3段階の構成にした
- Waylandコンポジタは実際にログインした仮想端末上でしか起動できないため、SSH経由ではなくログイン時に起動させる必要がある
- アプリ本体をlabwcのautostartではなくsystemdサービスにしているのは、 `Restart=always` でクラッシュ時の復帰をsystemdに任せられるため
- 画面の回転と輝度は作品ごとの変数で指定し、アプリを立ち上げる前に適用している
  - Touch Display 2は縦長が標準の向きのため、回転の指定が必要になる
  - 外部モニタにはsysfsのバックライトがないため、ミニPCでは輝度の設定を飛ばしている
- 作品の設定ファイルに `web_url` を書けばWebの作品、 `archive_url` を書けば実行ファイルの作品として扱う

### Webの作品

- Chromiumをキオスクモードで起動する
  - 復元ダイアログや初回起動ウィザードを抑止し、無人稼働中の余計な通信も止めるフラグを付けている
  - キオスクでは許可ダイアログに答えられないため、カメラを使う作品では、Chromiumのポリシーで作品のオリジンに限ってカメラを許可している

### 実行ファイルの作品

- GitHubのリリースからアーカイブを取得してチェックサムを照合し、展開したものを直接起動する
  - ラズパイ(aarch64)とミニPC(x86_64)でアーキテクチャが違うため、URLにはアーキテクチャ名を変数で埋め込み、端末に合ったアーカイブを選ばせている
  - アーカイブには、それを作ったMacのユーザのuidが記録されているため、展開時に所有者をrootに揃えている

## 会場のWi-Fiへの切り替え

- 会場のWi-Fiは現地に着くまで分からないことが多く、着いた時点では端末がどのネットワークにも繋がっていない可能性がある
- そこで、作業用PCと端末をEthernetで直結し、会場のWi-FiをNetworkManagerに登録してその場で繋ぎ替えるplaybookを用意した
- 登録したWi-Fiは消さずに残すため、以降は電波の届く範囲にあるものへ自動で繋がる
- 直結すると、追加の設定なしでIPv6のリンクローカルアドレスとmDNSによって `<ホスト名>.local` で到達できる
- ただし直結ではDHCPサーバがないため、NetworkManagerが1〜2分で接続を切ってしまう
  - playbookを流すには十分な時間なので、ケーブルを挿したらすぐに実行し、切れたら挿し直すことにしている

## おわりに

- 機材ごとの差分をOSのインストールとグループ変数に閉じ込められたので、別の作品や別のディスプレイの端末も同じAnsibleで増やしていきたい
- 一方で、映像ではない音響作品も制作しているため、それをこのプラットフォームでどう動かすかが今後の課題になる
